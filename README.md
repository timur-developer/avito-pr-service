# Сервис назначения ревьюеров Pull Request

Backend-сервис для управления командами, пользователями и Pull Request-ами с автоматическим назначением ревьюеров.

Сервис помогает распределять code review внутри команд: при создании PR автоматически выбираются до двух активных ревьюеров из команды автора, сам автор исключается из назначения. После merge состав ревьюеров фиксируется, а открытые PR поддерживают переназначение ревьюера на другого активного участника команды.

## Возможности

- создание и получение команд;
- управление активностью пользователей;
- создание Pull Request с автоматическим назначением ревьюеров;
- получение списка PR, назначенных пользователю на review;
- merge Pull Request в идемпотентном режиме;
- переназначение ревьюера в открытом PR;
- статистика по пользователям и их PR;
- массовая деактивация команды с переназначением ревьюеров;
- Swagger-документация для ручной проверки API.

- Go

- `slog` для логирования

## Запуск приложения

**Требования:**

- установленный и запущенный Docker;
- свободные порты:
  - `5432` для PostgreSQL;
  - `8080` для API;
  - `8081` для Swagger UI, если используется отдельный контейнер Swagger.

Склонируйте репозиторий и перейдите в папку проекта:

```bash
git clone <repository-url>
cd <project-directory>
```

Запустите контейнеры:

```bash
docker compose up --build
```

Для запуска в фоне:

```bash
docker compose up --build -d
```

После старта будут доступны:

- API: `http://localhost:8080`
- Swagger UI: `http://localhost:8080/docs`

## Остановка приложения

```bash
docker compose down
```

Сервис поддерживает graceful shutdown: при получении `SIGINT` или `SIGTERM` он завершает работу с таймаутом 5 секунд, корректно закрывая HTTP-сервер и соединения с базой данных.

## Документация API

Swagger UI доступен по адресу:

```text
http://localhost:8080/docs
```

Через Swagger можно посмотреть доступные endpoint-ы, схемы запросов и ответов, а также выполнить ручные запросы к сервису без Postman или curl.

## Основная бизнес-логика

При создании Pull Request сервис автоматически назначает до двух ревьюеров:

- ревьюеры выбираются из команды автора PR;
- автор PR не может быть назначен ревьюером;
- назначаются только активные пользователи;
- если доступен один активный ревьюер, назначается один;
- если подходящих ревьюеров нет, PR создается без назначенных ревьюеров.

Merge PR реализован идемпотентно: повторный merge уже закрытого PR не меняет состояние и возвращает актуальные данные. После merge список ревьюеров больше не изменяется.

Переназначение ревьюера доступно только для открытых PR. Новый ревьюер выбирается из команды старого ревьюера среди активных пользователей.

## Валидация и ошибки

Сервис выполняет два уровня проверок:

- валидация входного JSON;
- доменная валидация бизнес-правил.

Пользователю возвращаются структурированные коды ошибок, например:

- `NOT_FOUND`
- `CONFLICT`
- `INVALID_REQUEST`

Внутренние детали ошибок логируются через `slog`, но не раскрываются в API-ответах.

## Дополнительные возможности

### Статистика пользователей

Endpoint:

```text
GET /stats/users
```

Возвращает статистику по пользователям и их Pull Request-ам. В ответ включаются все пользователи, включая тех, у кого пока нет PR.

### Массовая деактивация команды

Endpoint:

```text
POST /team/deactivate
```

Пример тела запроса:

```json
{
  "team_name": "backend"
}
```

Деактивирует всех пользователей команды и переназначает ревьюеров в открытых PR, если для них есть подходящие активные кандидаты.

В ответе возвращается количество деактивированных пользователей и количество PR, где были выполнены переназначения.

## Нагрузочное тестирование

Нагрузочные тесты проводились с помощью `k6` по основным endpoint-ам сервиса.

Сервис выдерживает целевую нагрузку по времени ответа и RPS.
